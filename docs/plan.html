AgentControl Plan
Project plan · working draft

AgentControl

A local-first web app that runs Claude Code, Codex and other coding agents on your own machine or on SSH workspaces, shows which sessions are waiting on you, and lets each user rewrite the interface itself by asking a built-in agent.

Updated 22 Nov 2026Status: buildingAgents: Claude Code, Codex, Gemini CLI, OpenCode

Live status. What is done, in progress and not started is on the live status page, also kept in the repo as docs/status.html. Smaller deferred tasks are in TASKS.md. This plan holds the decisions and the reasons for them.

Why

What it must do

Run and watch agentsLaunch sessions locally or over SSH, see live output, thinking and diffs, and know at a glance which session needs an answer.
Own the interfaceThe whole web UI is user code. A built-in agent edits it on request, with keep, undo and full version history.
Learn from sessionsCost and behaviour analytics per session, model and workspace, so you can see what works and what wastes tokens.

Also in scope: configuring MCP servers, skills, hooks, instructions and every other harness setting from the UI, once, for every agent and workspace.

Architecture

How the pieces fit

Everything the user sees runs on their laptop. Workspaces run the agents and keep the authoritative event log, so the laptop is a viewer that catches up whenever it reconnects.

Local app API, live stream, sync, packaging

One binary per OS, started by the user. It serves the UI on localhost, holds the SQLite store, and keeps one SSH connection per workspace.

  • Opens each workspace with the system ssh so ~/.ssh/config, keys and jump hosts just work.
  • Copies relay events into SQLite, keyed by workspace, session and sequence number. On reconnect it asks for "everything after N".
  • Exposes commands and queries over HTTP, and one live stream (SSE or WebSocket). History and live events use the same shape, so the UI renders both with one code path.
  • Mounts Vite in middleware mode under / and serves the built-in /_safe page itself.
Relay the daemon on each workspace

The relay is built and runs on the laptop today. On SSH workspaces it will be deployed automatically on first connect (copied over SSH, started as a user service, phase 5). It must keep working with no laptop attached: it is a daemon on a unix socket (owner-only permissions) that keeps running when the app closes, and relay --stdio is a thin bridge that starts it when needed.

  • Spawns ACP adapters per session and answers them as the ACP client. Advertises no fs or terminal capability, so agents use their own tools on the workspace.
  • Appends every ACP message, unchanged, to a JSONL file per session with a sequence number. It also attaches normalised updates for the UI to read (see Abstractions below).
  • Holds pending permission requests until the user answers, even hours later.
  • Creates a git worktree per session, prepared by the repo's setup (below), and serves its diff on request.
  • Session diff = every change since the branch left its base, committed or not, new files included: the relay takes git merge-base <base> HEAD and diffs the working tree against it, staging untracked files into a throwaway index (GIT_INDEX_FILE) so the real index is never touched.
  • Archive: stops the agent if it is running, then removes the worktree but keeps its branch, so commits survive. If there are uncommitted changes, the user is warned first. The event log is kept, so archived sessions stay readable under an Archived filter.
  • Reads agent logs (~/.claude/projects, ~/.codex/sessions) or gateway logs for token and cost data.
  • Writes skills, hooks and MCP config into each agent's native locations.

Decided: our own thin relay. Rivet's sandbox-agent runs Claude Code and Codex behind a daemon too, but it is young (v0.5, first release Jan 2026, one npm maintainer) and speaks HTTP + SSE with its own event model, so we would need an adapter for every relay method. We do not build that.

Relay as built what the code does today

The relay runs on the laptop as the local workspace. Every item below has end-to-end tests that run against the mock agent.

  • Agents. One adapter process per session, started over stdio. The relay answers as the ACP client. A tap on the stream records every raw message in both directions, unchanged. The agent kinds today are claude-code, codex and the test-only mock.
  • Permission holding. A permission request waits until the user answers, however long that takes. A restart closes anything the dead process left open.
  • Event log. One append-only JSONL file per session. Every event gets the next sequence number for that session. The log survives crashes: a half-written last line is skipped, and the app resumes with "events after N".
  • Sessions. Created, prompted, cancelled and archived through the relay. The status (starting, running, waiting, idle, done, failed, archived) is derived from the events, never stored separately.
  • Worktrees. One per session, with the repo's files copied in, a setup script run, and a port block assigned. The diff since the base branch uses a throwaway git index, so the real one is never touched.
  • Files. Tree, read (at base, head or working copy) and write. A save must carry the hash the user last saw, or it is refused. Any path that would escape the worktree is refused.
  • Repos store. The repositories the relay knows about, each with its copy-files and setup-script settings.
  • Workspace check. A checklist of what works on this machine (git, agents, repos) for the setup screen.
  • Usage. Tokens and cost per finished turn, worked out from the events.
  • JSON-RPC over the socket. The 18 request methods and 2 notifications below, each with a zod schema in packages/protocol. The bridge and the daemon also work from a compiled binary.

The app side is built too: it connects to the relay and reconnects with backoff, copies events into SQLite, serves the HTTP API and one live SSE stream with Hono, and keeps UI versions in a hidden git repository. The default UI, the Modify agent and the Mac shell are still being built.

What the ACP spike taught us from docs/acp-notes.md

Tested with @agentclientprotocol/sdk 2.9.1, claude-agent-acp 0.109.1 and codex-acp 2.9.0. Claude Code is confirmed by real runs. Codex is not yet verified end to end: the OpenAI key we had has no quota, so only start-up and sign-in were seen.

  • The adapters bring their agent. Both packages bundle the agent binary, so no separate claude or codex install is needed. Claude's package is about 430 MB.
  • No session/set_model. The SDK has no such method. The model and thinking level are config options, set with session/set_config_option.
  • 19 update kinds, not 10. The first draft of this plan listed 10. The full list of 19 is in the message catalog below. The relay stores any kind it does not know, untouched.
  • Usage comes in two places. usage_update reports how full the context window is and the cumulative cost. Per-turn token counts come with the result of the prompt.
  • Diffs arrive with the permission request. Claude sends the old and new text inside session/request_permission, which is the diff to show on an approval screen. Permission option ids differ per adapter, so match on the option kind.
  • Loading a session replays it, coalesced. Both adapters can load a session, but the replay merges small chunks into whole messages. Replayed messages must not be appended to our log. Our own log of live messages stays the record; session/resume may suit better than load.
  • Codex reconnects quietly. It reports network trouble as a session_info_update and keeps retrying, so the relay needs its own turn timeout.
  • Thinking is unconfirmed. No thought chunks appeared in two small prompts, even at high effort.

Five changes in progress now, before more code sits on top:

  1. Normalised agent updates. The relay attaches agent-neutral updates (text, tool, plan, mode, notice, usage) to each event. Raw ACP stays in the log.
  2. A workdir with two kinds, git worktree and plain directory, so the Modify agent can run as an ordinary relay session.
  3. Live session summaries pushed by the relay, including pending permission requests. This also ends the full-log re-reads on every file or diff request.
  4. A workspace id on every live message, and a store key of workspace plus session.
  5. The UI reads all data through one client, which can be given a different fetch, for example one that replays a recorded session.

What waits. Phase 5: the workspace target, a version check on relay/hello, an event format version, an explicit agent environment, one sync per workspace, the suite run over SSH to a local sshd, and a test with two local relays. Phase 6: the agent registry with one translator per agent, and MCP servers passed in session/new. Phase 7: usage readers as a list, prices in the app, and analytics that read normalised updates, never raw ACP.

Never build: a transport or plugin framework; a dependency-injection container or injected id and clock generators nobody asserts on; other backends for the log or store without a requirement; an interface for other git hosts before a second host exists; an adapter that makes sandbox-agent look like our relay; dropping raw ACP from the log; a git abstraction for jj.

Adding a workspace one guided setup, re-runnable

Claude Code and Codex are assumed to be installed and signed in. Everything else is set up by the app, as a checklist that shows each step's status and can be run again at any time with Check and repair. The local machine goes through the same flow on first run, so the MVP uses it too.

  1. Connect. Pick a host from ~/.ssh/config or type one; test the connection and confirm the host key. (Skipped for the local machine.)
  2. Inspect. OS, CPU architecture, free disk space, git version and identity.
  3. Install the relay of the app's exact version, and start it so it keeps running after logout.
  4. Agents. Find Claude Code and Codex, install the pinned ACP adapters next to the relay, and run an ACP handshake with each one (no prompt, no tokens) to confirm it starts and is signed in.
  5. Repositories. Add folders that already exist on the workspace, or clone from a git URL. For each, set the repo's worktree setup (below).
  6. Configuration. Read what each agent already has (MCP servers, skills, hooks, instructions), offer to import it, then apply the user's global config (phase 6).
  7. Optional gateway for model routing and cost logs.

A step that fails says why and what to do; the workspace becomes usable once the required steps pass.

Worktree setup a ready-to-work copy for every session

A fresh worktree has no node_modules, no .env files and no build cache, and two agents running dev servers would fight over ports. Each repository therefore has setup settings, stored in the app's config at repo scope:

  • Files to copy from the main checkout into each new worktree. Default: .env*.
  • Setup script run once in the new worktree, for example bun install. Its output appears at the top of the session; if it fails, the session waits on the user before the agent starts.
  • Ports. Each session gets its own block of ports through environment variables (PORT and AGENTCONTROL_PORT_BASE), so parallel dev servers never collide.

Order on session create: add the worktree from the base branch, copy files, assign ports, run the setup script, then start the agent.

Dependencies the rule for adding one, and the audit (Nov 2026)

Bun first. Bun already gives us SQLite, the HTTP server, the test runner, process spawning, hashing, globbing, bun audit and single-binary builds. Git and SSH are the system tools on the workspace, and JSON-RPC framing is a few lines of our own. A library is added only when it does something we'd otherwise write hundreds of lines for.

The bar for a new dependency, checked by the orchestrator, the only one who adds dependencies (there are no pull requests):

  • Owned by a known organisation or a long-standing maintainer, with a release in the last 12 months.
  • Permissive license: MIT, Apache-2.0, BSD or ISC. Copyleft only for dev tools that never ship.
  • Few dependencies of its own. Prefer zero.
  • Exact versions pinned, bun.lock committed, new releases installed only when they are at least 14 days old (Bun's minimumReleaseAge, checked and working), updates via Dependabot. knip fails the build on any unused dependency.

ACP message catalog everything the relay handles

Client → agent

  • initialize, authenticate
  • session/new (cwd, MCP servers)
  • session/load (optional resume; the replay is coalesced, so it is not logged as new events)
  • session/prompt (open for the whole turn)
  • session/set_config_option (model and thinking level; the SDK has no session/set_model)
  • session/set_mode, session/cancel

Agent → client

  • session/request_permission (waiting on you)
  • session/update notifications
  • fs/* and terminal/*: not advertised remotely

Update kinds (19): user_message_chunk, agent_message_chunk, agent_thought_chunk, tool_call, tool_call_update (status, output, diff), plan, plan_update, plan_removed, available_commands_update, current_mode_update, config_option_update, session_info_update, usage_update (context fill and cost), notice, compaction_update, compaction_summary_chunk, subagent_update, session_message, session_message_chunk. Agents also push auth/status_update notifications.

Stop reasons: end_turn, max_tokens, max_turn_requests, refusal, cancelled. Extensions use _meta fields and underscore-prefixed methods.

Code editor for the worktree Monaco built in, VS Code on demand

Three levels, all open source or standard, so we build no editor ourselves:

  1. Built in: Monaco Editor. The editor component of VS Code (MIT). The Changes tab uses its diff editor (base vs working copy, side by side or inline). The Editor tab opens any worktree file with syntax highlighting, search, multi-cursor and go-to-line. Files come from the relay through fs.tree, fs.read and fs.watch, so the view updates as the agent edits.
  2. Full IDE in the browser: code-server (Coder, MIT, actively released). The relay starts it on the workspace, pointed at the session's worktree. The local app forwards its port over the existing SSH connection and opens it in a new tab, with extensions, terminal and language servers.
  3. Desktop editor. A vscode://vscode-remote/ssh-remote+<host>/<worktree> link opens desktop VS Code on the same folder through Remote-SSH. Cursor and other forks use the same pattern with their own scheme.

Editing while an agent runs. Saves go through fs.write with the hash the user last saw. If the agent changed the file since, the save is refused and the editor shows the new version. By default the editor is read-only while a turn is in progress and editable between turns.

Monaco is used directly, not through @monaco-editor/react: that wrapper has one maintainer, no release since Feb 2025, and loads Monaco from a CDN by default, which a local-first app shouldn't do.

Harness configuration

Configure every agent from one place

Each harness keeps MCP servers, skills, hooks and instructions in its own files and formats. The app holds one canonical version of all of it, lets you edit it in the UI, and the relay writes the right files for each agent on each workspace.

WhatConfigured in the UI
MCP serversCommand or URL, arguments, env vars and secrets, which agents and workspaces get them. Test a server before enabling it.
SkillsBrowse, create and edit SKILL.md folders; install from a skills registry; enable per agent and scope.
HooksEvents such as before a tool runs, after an edit, at session start or stop; written once, translated to each agent's hook format.
InstructionsGlobal and per-repo instructions, written to CLAUDE.md, AGENTS.md or GEMINI.md as each agent expects.
Subagents and commandsCustom agents and slash commands, converted to skills where a harness has no equivalent.
PermissionsAllowed and denied tools, approval mode, sandbox level.
DefaultsDefault model and thinking level, gateway on or off, environment variables per workspace.

Every item has a scope: global (all workspaces), workspace, or repo. Narrower scopes override wider ones, and the UI shows the effective config for any session before it starts.

How a change is deployed inspect, plan, apply
  1. Inspect. The relay reads what each agent has today on the workspace. On first connect, the UI offers to import it, so existing setups aren't lost.
  2. Plan. The relay translates the canonical items into each agent's native files and returns the file-level diff. The UI shows it before anything is written.
  3. Apply. The relay backs up the touched files, writes the new ones, and reports per agent. Rollback restores the backup.
  4. Watch for drift. The relay rechecks file hashes on connect. If someone edited a file by hand, the item is marked as drifted with options to adopt the change or overwrite it.

Only files the app manages are touched. Managed entries carry a marker so hand-written config around them is left alone.

Per-session config through ACP no files written

MCP servers can also be passed in session/new, which starts them for that session only. Use this for one-off or experimental servers, and for secrets you don't want written to disk: the relay injects them as environment variables when it starts the server.

The malleable part

How the UI rewrites itself

The UI is a small web project inside the app's data folder. A built-in Modify agent edits it on request. The user only sees the result and two buttons: Keep and Undo.

  1. The user asks for a change, for example "add a cost column and sort by it".
  2. The Modify agent, a local ACP session of Claude Code or Codex, edits a staging copy of the UI.
  3. A typecheck and build run after each edit. Errors go back to the agent until they pass.
  4. The finished change is copied to the live folder at once, and Vite hot-reloads it.
  5. Keep commits the change to a hidden git repository, with the request as the message. Undo goes back one commit.
Never lock the user out. /_safe is served by the app, not by the user's UI. It always shows the Modify chat and the version history, so any broken change can be rolled back in one click.
Folder layout and agent rules 
~/.agentcontrol/
├─ state.db
├─ ui.git/              UI history (kept outside the agent's folder)
├─ ui/                  live UI (served by Vite)
├─ ui-staging/          Modify agent's working copy
└─ ui/AGENTS.md         rules for the Modify agent
  • Data only through @agentcontrol/sdk; never call the API directly.
  • Only bundled libraries are available. No npm install.
  • Prefer editing layout.json for arrangement changes; put new features in your own files, plugged into the default UI's named slots, instead of editing default components.
  • Run the check command before finishing.

The Modify agent is fenced in. It may edit files only inside ui-staging/; it runs no shell commands (the app runs the checks itself and sends back the result) and has no web access beyond its model's API. This is enforced twice: through the agent's own permission settings, and by the app automatically refusing any other permission request the agent sends.

Why hot reload is instant

Vite serves each source file as its own ES module and keeps a WebSocket open to the page. When a file changes, it converts only that file and tells the browser to re-import it; React Fast Refresh swaps the component in place and keeps its state. Cost scales with the size of the change, not the app.

Changes in a non-component file bubble up to the nearest importer that can accept them, or trigger a full page reload. That is why the agent works in staging and the live folder gets one clean update.

Updating the default UI merge, agent fixes conflicts, checks, Keep or Undo
  1. The new app version commits its default UI onto upstream.
  2. In the staging folder, upstream is merged into main. Clean merges need nothing more.
  3. For each conflict, the Modify agent gets the conflicted files and the original requests behind the user's changes, so it rebuilds what the user wanted, not just the old lines.
  4. The usual checks run: typecheck, build, lint, and a browser test that the UI loads.
  5. The user sees a summary, for example "Update 1.2: 4 of your changes kept automatically, 1 conflict resolved (cost column moved to the new session table)", then Keep or Undo.

Merge, not rebase. A rebase replays each change one by one, so one conflict can come back several times. A merge brings both histories together once, so each conflict is resolved once. The result is the same: the user's changes on top of the latest default UI.

An update never breaks the UI. If the agent can't make the checks pass, the current UI keeps running, the update waits, and /_safe still rolls back.

Keeping conflicts rare.

  • Layout changes go in layout.json; data merges far more cleanly than code.
  • New features go in the user's own files, plugged into named slots the default UI provides (session row, toolbar, side panels), so template updates rarely touch them.
  • @agentcontrol/sdk stays backward compatible: a function is deprecated for one release before removal. If a removal slips through, the typecheck catches it during the update.
Versions and history a hidden git repository 
upstream:  v1.0 ─────────── v1.1 ─────────── v1.2      default UI from each app release
             \                \                \
main:         A ── B ── C ──── M1 ── D ── E ──── M2     your changes (A–E), updates (M)
  • Git without installing git. isomorphic-git is bundled in the app; Macs have no git until the developer tools are installed.
  • Two branches. upstream gets one commit per default UI version. main is the user's UI: every Keep is a commit whose message is the original request.
  • The agent never sees git. The repository lives in ui.git/, outside the folder the Modify agent works in, so it can't commit, reset or rebase by itself.
  • Undo and history are the commit log. Undo is a new commit restoring the previous state, so nothing is ever lost.
  • Sharing exports one version as a single file. Importing someone else's UI shows its diff first, because it runs with full access to your agents.

Code architecture and quality

Maintainable by default, enforced by the build

The code must stay easy to change after hundreds of agent-written commits. The rules are written down once in AGENTS.md, and every rule a tool can check is checked on every push. A rule only in a document will be broken; a rule in CI breaks the build instead.

Principles

  • Single responsibility first. One module, one reason to change. If describing a file needs "and", split it.
  • KISS. Plain functions and modules. No abstraction until the second real use, no DI framework, no clever types, no utils/ dumping ground.
  • Open/closed where it pays. Agents and harness translators sit behind one small interface each, so adding an agent means adding one adapter.
  • Small interfaces, injected edges. Logic receives its store, transport and clock as parameters. Only the edges (ACP, SSH, SQLite, fs, HTTP) touch the outside world.

Tests

  • End-to-end only. No unit tests. Every test starts the real app and relay and drives them as a user would.
  • GIVEN / WHEN / THEN with a plain-language sentence at every step, saying exactly what is set up, done and checked.
  • Setup helpers and assertion helpers named after the domain fact, so the test reads as a specification.
  • The only fake is the agent: a scripted mock ACP agent, so tests are deterministic and need no API key.
  • At least 95% of lines covered by the end-to-end suite, in total and on changed lines, before any push.
Code architecture packages, features, dependency rules 
ui-template ──▶ sdk ──HTTP──▶ app ──SSH/JSON-RPC──▶ relay ──ACP──▶ agents
                 │             │                      │
                 └──────────▶ protocol ◀──────────────┘   (protocol imports nothing)
  • Feature folders inside each package, not layers: relay/src/sessions/, relay/src/worktrees/, relay/src/config/. Each feature exposes one index.ts; other features import only that.
  • Thin edges, plain core. Adapters translate ACP, SSH, SQLite and HTTP into plain data; the logic in between is ordinary functions over that data.
  • Dispatch tables over long switches. ACP update kinds map to one small handler each, which keeps every function under the complexity limit.
  • Package rules are enforced: the UI talks only to the SDK, the relay never imports the app, nothing imports a feature's internals, and there are no circular imports.
How tests are written given / when / then, with readable helpers

  • GIVEN, WHEN and THEN each open a block with a three-line banner comment (// **** / // ** GIVEN … / // ****), so the three phases stand out at a glance. Extra steps inside a block use a single // AND … line. Every comment says in plain words what is set up, done or checked; the code under it is one or two helper calls. Browser tests follow the same layout.
  • One behaviour per test. The test name is a sentence about what the user sees.
  • No logic in tests: no if, loops or sleeps. Helpers wait for events instead of sleeping.
  • Every test gets its own data folder and workspace, so tests run in parallel and never share state.
  • Assertion helpers fail with a human message: expected session "Add rate limiting" to be waiting for approval, but it is running.

Development loop how parallel agents change the code without breaking main

From docs/dev-loop-review.md, written after seven agents worked at once, main had never been green, and several finished commits were stuck. The orchestrator is Claude; coding subagents (Sonnet) and research subagents (Opus) do the work.

  • One worktree and one branch per agent, started from the latest main and kept outside the tools' view (the agent worktree folder is ignored by git and ESLint). An agent edits only the paths its brief names (docs/brief-template.md is the template).
  • Contracts first. Before a parallel wave, the orchestrator commits the interfaces as code: zod schemas and types in packages/protocol, new SDK signatures, and the end-to-end tests for the feature written as test.todo with full GIVEN / WHEN / THEN bodies. The agents turn the todos into passing tests. If a contract is wrong, the agent stops and reports.
  • An integrate script is the only way onto main. bun run integrate <branch> rebases the branch in a scratch worktree, runs the full check there, and only then moves main (a fast-forward). If main moved in the meantime it stops and is run again. If main ever goes red, the offending commit is reverted first, before anything else.
  • Parallel, timed gates and a quick check. bun run check starts every gate at once, prints seconds per gate and shows all failures. bun run check:quick checks only the changed files and finishes in seconds.
  • A done report. bun run done <paths> runs the full check, fails when files outside the owned paths changed, when a dependency changed, when eslint.config.js changed, or when a new eslint-disable was added, and prints a DONE-REPORT block the orchestrator reads instead of prose.
  • Guardrails. No git add -A or git add .. No repo-wide formatting (bun run format touches only changed files). Dependencies are added only by the orchestrator: a pre-commit guard blocks anyone else from changing bun.lock or a package.json dependency list. Gate samples are written in a scratch copy, so a bad sample is never committed by accident.
  • A decision log. One short file per decision in docs/decisions/ (context, decision, rejected options, consequences), written on the agent's branch so it merges with the code. The first file, 0001, records these decisions.
  • Planned: golden files for the durable state. Real event logs (including one cut off mid-line), a snapshot of the relay protocol with a protocol version number that must change when a field is removed, an old state.db per migration that the app must still open, and an old hidden UI repository that must upgrade cleanly. Also planned: a coverage map of every relay method, event kind and API route, a timing budget per test, a nightly flake run, and a status page generated from the repository.
AGENTS.md the first file in the repository

Written before any code. Codex and OpenCode read AGENTS.md directly; CLAUDE.md contains only @AGENTS.md so Claude Code reads the same rules, and Gemini CLI is pointed at it through its context file setting. One source, every agent.

  1. Principles: SOLID with the S first, KISS, with a short example of each.
  2. Structure: packages, feature folders, the dependency rules above.
  3. Tests: end-to-end only, given / when / then, helper naming, a full example test.
  4. Quality gates: each limit and the expected fix: split the function, never raise the limit or disable the rule.
  5. Commands: bun dev, bun run test, bun run check.
  6. Definition of done, in this order: new behaviour has an end-to-end test that reads as a specification and line coverage stays at 95% or more; bun run check passes; the agent runs /code-review on its own diff and fixes what it finds; the plan, and TASKS.md for the long tail, say what changed.
  7. Working in parallel: one worktree and branch per agent, only the paths in its brief, no git add -A, no repo-wide formatting, no dependency changes (the orchestrator does those), decisions written to docs/decisions/, and revert first if main goes red.

Risks and open questions

Risks

  • ACP adapters lag behind native CLIs; some features may never appear in events.
  • Agent-written UI code breaks in ways a typecheck misses.
  • Thinking varies by vendor: summaries rather than raw reasoning.
  • Shared UIs are code with full access to your agents.
  • Config formats change between harness versions and can silently break translations.
  • Aggressive limits slow early work and invite rule disabling; the reason-required rule and review must hold the line.
  • An e2e-only suite is slower; it must stay parallel and free of sleeps to keep feedback fast.
  • Codex is unverified end to end. Only start-up and sign-in were seen; streaming, diffs and permissions are not confirmed.
  • The Mac app has never been built on a Mac. Expect fixes on the first run of the build workflow.
  • CI is currently red. It is set up and being fixed; until it is green, main is checked only by the integrate script.
  • Coverage needs an in-process test mode, which gives up some process isolation in most tests. A small set of real-process tests has to make up for it.
  • The mock agent may drift from the real adapters, so tests pass while real agents behave differently. Recordings of real sessions are the planned check.

Open questions

  • Subscription login or API keys per agent, which decides the gateway.
  • How much of the default UI is layout data vs components.
  • Where behaviour analytics run: rules, or an agent reviewing sessions.
  • Should the app own all harness config, or only the items it created?
  • Allow editing files while an agent is mid-turn, or lock the editor until the turn ends?
  • External trajectories. Import read-only for viewing only, or as sessions that can be resumed? Imported by the app (cloud trace systems) or by the relay (agent logs on the workspace)? And what about sessions started outside the app?
  • Containers or cloud sandboxes as workspaces. In scope after SSH, or never? It decides whether a workspace target stays at two kinds.
  • How pull requests are created: gh on the workspace with its own login, or the GitHub API from the app with a token in the keychain.
  • Relay version skew. Running sessions keep the old relay after an update. Does the app then talk to two relay versions on one workspace?
  • The Apple Developer ID. The owner needs one, for signing and notarisation.
  • Final product name. AgentControl is a working name (the name is taken elsewhere); the rename touches the SDK scope, data folder, dmg and cask.
  • The 14-day release age. Keep it, or shorten it so security fixes arrive sooner.

Decided and removed from this list: own relay (built), how work is merged (straight to main), the TypeScript version (pinned to 6.0.x), and the menu bar shell (a Swift app). The long tail of smaller tasks is in TASKS.md.

Market scan

No existing product covers all three goals. These are worth studying or reusing.

Multi-agent desktop apps Emdash, Superset, Zeron, Conductor, y
  • Emdash (open source, YC W26): worktree per task, diff review, PRs, installs hooks to track agent status.
  • Superset: runs any CLI agent, notifies when attention is needed, built-in diff viewer and editor.
  • Zeron: native control plane with live branch diff, local-first daemon, optional multi-device sync.
  • Conductor: polished, macOS only, Claude Code, Codex and Cursor.
  • y: closest to our idea; a malleable app with a protected kernel and an editable userland UI with snapshots.
  • Daemon references: Paseo, blemeesd, Codecast (auto-deploys its daemon over SSH).
Skills, hooks and MCP sync crossby, omni-skills, agents
  • crossby: syncs skills, permissions, hooks and MCP, translated per tool.
  • omni-skills: one canonical store; hooks transpiled into each tool's format.
  • agents (amtiYo): .agents source of truth for MCP, skills and instructions; no hooks.
  • vercel-labs/skills: installs skills across 35+ agents.
Session analytics ccusage, CodeBurn, LangWatch
  • ccusage: reference parser for local agent logs; cost by day, session and 5-hour block.
  • CodeBurn: cost by project, branch, task and PR with optimization suggestions.
  • LangWatch: OpenTelemetry traces per session, including idle time waiting on the user.
  • context-analyzer: shows how cost per call grows with context size.
