AgentControl

A local-first web app that runs Claude Code, Codex and other coding agents on your own machine or on SSH workspaces, shows which sessions are waiting on you, and lets each user rewrite the interface itself by asking a built-in agent.

Updated 24 Nov 2026, 18:45 UTCStatus: buildingAgents: Claude Code, Codex, Gemini CLI, OpenCode

Live status. What is done, in progress and not started is on the live status page, also kept in the repo as docs/status.html. Smaller deferred tasks are in TASKS.md. This plan holds the decisions and the reasons for them.

Why

What it must do

Run and watch agentsLaunch sessions locally or over SSH, see live output, thinking and diffs, and know at a glance which session needs an answer.
Own the interfaceThe whole web UI is user code. A built-in agent edits it on request, with keep, undo and full version history.
Learn from sessionsCost and behaviour analytics per session, model and workspace, so you can see what works and what wastes tokens.

Also in scope: configuring MCP servers, skills, hooks, instructions and every other harness setting from the UI, once, for every agent and workspace.

Architecture

How the pieces fit

Everything the user sees runs on their laptop. Workspaces run the agents and keep the authoritative event log, so the laptop is a viewer that catches up whenever it reconnects.

Local app API, live stream, sync, packaging

One binary per OS, started by the user. It serves the UI on localhost, holds the SQLite store, and keeps one SSH connection per workspace.

  • Opens each workspace with the system ssh so ~/.ssh/config, keys and jump hosts just work.
  • Copies relay events into SQLite, keyed by workspace, session and sequence number. On reconnect it asks for "everything after N".
  • Exposes commands and queries over HTTP, and one live stream (SSE or WebSocket). History and live events use the same shape, so the UI renders both with one code path.
  • Serves the UI under / from a Vite dev server that runs as a supervised child process (restarted if it dies, stopped when the app is gone), and serves the built-in /_safe page itself.

Built today, all with end-to-end tests:

  • Security guard (security/): one middleware on the root app checks Host and Origin and the secret token for every route, the live stream and every page. It puts the token into the pages the app serves itself. See Key decisions.
  • Preview route (preview/): GET /preview/<ticket>/<path>, outside /api. A ticket is minted by POST /api/sessions/:id/preview. File bytes come from relay/fs.readBytes, so images and fonts arrive intact. Every response carries the sandbox Content-Security-Policy.
  • Modify feature (modify/, ui-workspace/, ui-versions/, safe/): the Modify agent runs as a relay directory session. A small state machine moves a request through working, checking, fixing and ready (or failed); the app runs the typecheck and build itself and sends failures back to the agent. A promoted change that waits for Keep or Undo survives an app restart. Default-UI updates merge upstream into main and use the same machine. /_safe is a page of the app's own that needs neither the UI folder nor the SDK.
  • Config feature (api/config.ts, store/config-items.ts): the canonical harness-config items and where they apply live in two SQLite tables; import, plan, apply, rollback and drift go to the relay. The SDK has the calls. There is no screen for it yet.
  • Usage route: GET /api/sessions/:id/usage asks the relay for tokens and cost per finished turn.
  • Resources and embedded migrations (resources/, store/migrations.generated.ts): one function finds the release folder, the relay and the default UI (environment variable, next to the binary, a Mac bundle, or the source checkout). Database migrations are compiled into the binary, and a test fails when the generated file is behind the drizzle/ folder.
  • Workspace routing seam (api/routing.ts): routes ask for a workspace's relay link here and nowhere else. Today there is one local workspace.
Relay the daemon on each workspace

The relay is built and runs on the laptop today. On SSH workspaces it is deployed automatically on first connect (copied over SSH and started by the bridge, phase 5; built, checked only against a local sshd). It must keep working with no laptop attached: it is a daemon on a unix socket (owner-only permissions) that keeps running when the app closes, and relay --stdio is a thin bridge that starts it when needed.

  • Spawns ACP adapters per session and answers them as the ACP client. Advertises no fs or terminal capability, so agents use their own tools on the workspace.
  • Appends every ACP message, unchanged, to a JSONL file per session with a sequence number. It also attaches normalised updates for the UI to read (see Abstractions below).
  • Holds pending permission requests until the user answers, even hours later.
  • Creates a git worktree per session, prepared by the repo's setup (below), and serves its diff on request.
  • Session diff = every change since the branch left its base, committed or not, new files included: the relay takes git merge-base <base> HEAD and diffs the working tree against it, staging untracked files into a throwaway index (GIT_INDEX_FILE) so the real index is never touched.
  • Archive: stops the agent if it is running, then removes the worktree but keeps its branch, so commits survive. If there are uncommitted changes, the user is warned first. The event log is kept, so archived sessions stay readable under an Archived filter.
  • Works out tokens and cost per finished turn from the agent's own usage messages (built); the app copies each session's rows into its usage table for analytics (built). Reading agent logs (~/.claude/projects, ~/.codex/sessions) or gateway logs is planned.
  • Writes skills, hooks, MCP servers, instructions, commands, permissions and env into each agent's native files, entry by entry (built, relay/src/config/; see Harness configuration).

Decided: our own thin relay. Rivet's sandbox-agent runs Claude Code and Codex behind a daemon too, but it is young (v0.5, first release Jan 2026, one npm maintainer) and speaks HTTP + SSE with its own event model, so we would need an adapter for every relay method. We do not build that.

Relay as built what the code does today

The relay runs on the laptop as the local workspace. Every item below has end-to-end tests that run against the mock agent.

  • Agents. One adapter process per session, started over stdio. The relay answers as the ACP client. A tap on the stream records every raw message in both directions, unchanged. The agent kinds today are claude-code, codex and the test-only mock. Adapter versions are pinned in agents/adapters.ts and downloaded into the relay's own folder on first use. Real Claude Code is switched to Manual mode right after session/new, so it asks before acting.
  • Agent updates. A dispatch table in acp-normalise/ is the only code that knows ACP update shapes. It turns each message into agent-neutral updates (text, thought, plan, tool, mode, notice, usage, turn end) that are attached when an event is served, never stored.
  • Permission holding. A permission request waits until the user answers, however long that takes. A restart closes anything the dead process left open.
  • Event log. One append-only JSONL file per session. Every event gets the next sequence number for that session. The log survives crashes: a half-written last line is skipped, and the app resumes with "events after N".
  • Sessions. Created, prompted, cancelled and archived through the relay. The status (starting, running, waiting, idle, done, failed, archived) is derived from the events, never stored separately. The relay folds each log once at start-up and then keeps a live summary per session in memory (with turnRunning and the pending permission requests), and pushes changes as relay/sessions.changed. A restart kills the agents, so a request left open can never be answered: recovery appends agent-exited, and the session reads failed or idle.
  • Two kinds of session. The relay's folder operations sit behind a Workdir (workdirs/). A worktree session works in its own git worktree. A directory session works in a plain folder with no git: nothing to remove, no diff. The Modify agent is a directory session. The relay itself answers every permission request of a directory session: only a file edit whose paths all resolve (symlinks followed) inside the allowed folder is approved, everything else is refused. Both outcomes are logged as automatic answers.
  • Worktrees. One per session, with the repo's files copied in, a setup script run, and a port block assigned. The diff since the base branch uses a throwaway git index, so the real one is never touched.
  • Files. Tree, read (at base, head or working copy), readBytes (the working copy as base64, up to 10 MiB, for images and the Preview tab) and write. A save must carry the hash the user last saw, or it is refused. Any path that would escape the worktree is refused, so is any .git segment, and readBytes also refuses .env*, .npmrc and .netrc.
  • Repos store. The repositories the relay knows about, each with its copy-files and setup-script settings.
  • Workspace check. A checklist of what works on this machine (git, agents, repos) for the setup screen.
  • Usage. relay/usage: tokens and cost per finished turn, worked out from the events. A cancelled turn's tokens are read from the agent's quota data, because its own usage is all zeros.
  • Config. relay/config.*: inspect what Claude Code and Codex have today, plan, apply, rollback and drift, with a manifest, backups and byte-for-byte rollback.
  • JSON-RPC over the socket. The 24 request methods and 3 notifications below, each with a zod schema in packages/protocol. The bridge and the daemon also work from a compiled binary.

The app side is built too: it connects to the relay and reconnects with backoff, copies events and live summaries into SQLite, serves the HTTP API and one live SSE stream with Hono, keeps UI versions in a hidden git repository, and runs the Modify agent. The default UI is connected to it. The Mac menu bar shell is written and builds on a Mac runner, but nobody has run it (see Getting started).

What the ACP spike taught us from docs/acp-notes.md

Tested with @agentclientprotocol/sdk 2.9.1, claude-agent-acp 0.109.1 and codex-acp 2.9.0. Claude Code is confirmed by real runs, including nine scenarios through the whole app (edit with approval, reject, cancel, a second prompt, usage, restarts, archive, Modify). Codex is not yet verified end to end: the OpenAI key we had has no quota, so only start-up and sign-in were seen.

  • The adapters bring their agent. Both packages bundle the agent binary, so no separate claude or codex install is needed. Claude's package is about 430 MB.
  • No session/set_model. The SDK has no such method. The model and thinking level are config options, set with session/set_config_option.
  • 19 update kinds, not 10. The first draft of this plan listed 10. The full list of 19 is in the message catalog below. The relay stores any kind it does not know, untouched.
  • Usage comes in two places. usage_update reports how full the context window is and the cumulative cost. Per-turn token counts come with the result of the prompt.
  • Diffs arrive with the permission request. Claude sends the old and new text inside session/request_permission, which is the diff to show on an approval screen. Permission option ids differ per adapter, so match on the option kind.
  • Loading a session replays it, coalesced. Both adapters can load a session, but the replay merges small chunks into whole messages. Replayed messages must not be appended to our log. Our own log of live messages stays the record; session/resume may suit better than load.
  • Codex reconnects quietly. It reports network trouble as a session_info_update and keeps retrying, so the relay needs its own turn timeout.
  • Thinking is unconfirmed. No thought chunks appeared in two small prompts, even at high effort.
  • Claude starts in the user's own mode. It was auto on the test machine, where it never asks. The relay switches it to Manual (see Key decisions). Only edits and commands that change something ask; read-only commands and reads do not.
  • A cancelled turn reports zero tokens. The real numbers are in _meta.quota, which the relay reads.
  • Resume after a relay restart is built. A session whose agent was alive when the relay stopped reads interrupted; its pending permission requests are dropped and the log says so. relay/sessions.resume (also POST /api/sessions/:id/resume, sdk.sessions.resume, and implicitly the next prompt) starts a new adapter in the same worktree and calls session/load with the stored agent session id when the agent supports it; the replayed history is not logged again. Otherwise it starts afresh and the log says earlier context was not restored. The UI shows an Interrupted banner with Resume. Tested with the mock agent and over ssh; a real Claude Code or Codex session load through the relay is not verified (no API key in the build environment). Open: interrupted sessions are not yet counted as waiting on you, and the chat shows a stray "agent exited" line before the notice. Details: docs/decisions/2026-11-23-session-resume.md.
  • Modify launch limits were accepted by the real Claude adapter: the agent never had a Bash tool, and the user's own slash commands were gone. Codex gets no launch limits; for it the relay's permission answers are the only fence.

The five changes that had to land before more code sat on top: all five are done.

  1. Normalised agent updates. Done. The relay attaches agent-neutral updates (text, tool, plan, mode, notice, usage) to each event. Raw ACP stays in the log.
  2. A workdir with two kinds, git worktree and plain directory. Done: the Modify agent runs as an ordinary relay session.
  3. Live session summaries pushed by the relay, including pending permission requests. Done. This also ended the full-log re-reads on every file or diff request.
  4. A workspace id on every live message, and a store key of workspace plus session. Done (migration 0001).
  5. The UI reads all data through one client, which can be given a different fetch, for example one that replays a recorded session. Done: the client and its fetch option exist and the UI uses them. Nothing replays a recorded session through it yet.

What waits. Phase 5 has built the workspace target, the version check on relay/hello, one sync per workspace and the suite run over SSH to a local sshd (23 Nov 2026). Still waiting from phase 5: an event format version and an explicit agent environment. Phase 6: the agent registry, and MCP servers passed in session/new. Also still open: the relay accepts a model on sessions.create and drops it; the event format has no version of its own yet (the relay and app share one VERSION constant, which the handshake compares). Phase 7: usage readers as a list, prices in the app, and analytics that read normalised updates, never raw ACP.

Adding a workspace one guided setup, re-runnable

Claude Code and Codex are assumed to be installed and signed in. Everything else is set up by the app, as a checklist that shows each step's status and can be run again at any time with Check and repair. The local machine goes through the same flow on first run, so the MVP uses it too.

  1. Connect. Pick a host from ~/.ssh/config or type one; test the connection and confirm the host key. (Skipped for the local machine.)
  2. Inspect. OS, CPU architecture, free disk space, git version and identity.
  3. Install the relay of the app's exact version, and start it so it keeps running after logout.
  4. Agents. Find Claude Code and Codex, install the pinned ACP adapters next to the relay, and run an ACP handshake with each one (no prompt, no tokens) to confirm it starts and is signed in.
  5. Repositories. Add folders that already exist on the workspace, or clone from a git URL. For each, set the repo's worktree setup (below).
  6. Configuration. Read what each agent already has (MCP servers, skills, hooks, instructions), offer to import it, then apply the user's global config (phase 6).
  7. Optional gateway for model routing and cost logs.

A step that fails says why and what to do; the workspace becomes usable once the required steps pass.

Built (23 Nov 2026): the Workspaces menu in the top bar and the Add workspace dialog (pick or type a host, then connecting, checking, and the checklist; a failed step is named with its detail and Retry runs the checklist again, which also installs a missing relay). Check and repair, Restart relay (only when the relay needs an update, after a warning) and Remove are in the same menu. The dialog shows no live progress inside a step, because the app answers once. Decisions and the remaining gaps: docs/decisions/2026-11-23-ui-workspaces-and-config.md.

Worktree setup a ready-to-work copy for every session

A fresh worktree has no node_modules, no .env files and no build cache, and two agents running dev servers would fight over ports. Each repository therefore has setup settings, stored in the app's config at repo scope:

  • Files to copy from the main checkout into each new worktree. Default: .env*.
  • Setup script run once in the new worktree, for example bun install. Its output appears at the top of the session; if it fails, the session waits on the user before the agent starts.
  • Ports. Each session gets its own block of ports through environment variables (PORT and AGENTCONTROL_PORT_BASE), so parallel dev servers never collide.

Order on session create: add the worktree from the base branch, copy files, assign ports, run the setup script, then start the agent.

Dependencies the rule for adding one, and the audit (Nov 2026)

Bun first. Bun already gives us SQLite, the HTTP server, the test runner, process spawning, hashing, globbing, bun audit and single-binary builds. Git and SSH are the system tools on the workspace, and JSON-RPC framing is a few lines of our own. A library is added only when it does something we'd otherwise write hundreds of lines for.

The bar for a new dependency, checked by the orchestrator, the only one who adds dependencies (there are no pull requests):

  • Owned by a known organisation or a long-standing maintainer, with a release in the last 12 months.
  • Permissive license: MIT, Apache-2.0, BSD or ISC. Copyleft only for dev tools that never ship.
  • Few dependencies of its own. Prefer zero.
  • Exact versions pinned, bun.lock committed, new releases installed only when they are at least 14 days old (Bun's minimumReleaseAge, checked and working), updates via Dependabot. knip fails the build on any unused dependency.

Code editor for the worktree Monaco built in, VS Code on demand

Three levels, all open source or standard, so we build no editor ourselves:

  1. Built in: Monaco Editor. The editor component of VS Code (MIT). The Changes tab uses its diff editor (base vs working copy, side by side or inline). The Editor tab opens any worktree file with syntax highlighting, search, multi-cursor and go-to-line. Files come from the relay through fs.tree, fs.read and fs.watch, so the view updates as the agent edits.
  2. Full IDE in the browser: code-server (Coder, MIT, actively released). The relay starts it on the workspace, pointed at the session's worktree. Built 24 Nov 2026 (docs/decisions/2026-11-23-browser-vscode.md): code-server is the user's own tool, found on the workspace's PATH and never installed by us. One per session, listening on a private unix socket with no TCP port, stopped on archive, relay stop, crash and after 30 minutes idle. It is reached through the existing relay link (relay/ide.*, with a 1 MiB credit window so an unread download stalls instead of piling up) and served on a second local port, a different origin from the app, under a ticket path; cookies and authorization headers are dropped. Tested with a stand-in; the real workbench is not verified yet.
  3. Desktop editor. A vscode://vscode-remote/ssh-remote+<host>/<worktree> link opens desktop VS Code on the same folder through Remote-SSH. Cursor and other forks use the same pattern with their own scheme.

Editing while an agent runs. Saves go through fs.write with the hash the user last saw. If the agent changed the file since, the save is refused and the editor shows the new version. By default the editor is read-only while a turn is in progress and editable between turns.

Monaco is used directly, not through @monaco-editor/react: that wrapper has one maintainer, no release since Feb 2025, and loads Monaco from a CDN by default, which a local-first app shouldn't do.

Preview tab HTML and Markdown files, shown inside the app built

A Preview tab next to Changes and Editor shows a file from the session's worktree, the way an HTML artifact is shown beside a chat. Design and reasons: docs/decisions/2026-11-22-preview-sandbox.md and 2026-11-22-markdown-preview.md.

HTML files. The page runs in an iframe with sandbox="allow-scripts allow-forms" (never allow-same-origin), so it has no access to the app's storage or API. The app serves it from /preview/<ticket>/ with a Content-Security-Policy that lets it load only its own folder, data: and blob:. A ticket is a random capability for one session: it lives in memory, ends an hour after last use, on archive and on restart. Bytes are read through relay/fs.readBytes, so images and fonts are not damaged. A page with its own CSS, scripts and images in the same folder works. The preview reloads when files in the page's folder change (250 ms pause) and on Reload.

Markdown files. Rendered in the browser with marked, cleaned with DOMPurify (scripts, event handlers, forms, SVG and more are removed), and shown in the same kind of frame but with a stricter sandbox: no scripts at all. Relative images and links are rewritten to the file's folder.

Limits, on purpose or not fixed yet:

  • A page cannot use fetch, XHR or WebSockets (connect-src 'none'), so a page that loads its own JSON file with fetch does not work. Scripts, styles and images do.
  • The scroll position is lost on refresh: the app cannot read it from a frame with an opaque origin.
  • Editing a file outside the page's own folder (../css/x.css) does not refresh the page until Reload.
  • Files up to 10 MiB; no range requests, so large video does not seek.
  • The relay refuses .env*, .npmrc and .netrc by name and by link target; files a repo's copy-files setting adds under other names are not protected. A hostile page could still send its own scripts and styles, and its address, to another site. A browser too old to send Sec-Fetch-Dest is not covered.
Console a terminal on the workspace, inside the app built

A Terminal tab next to Changes, Editor and Preview opens a real shell on the session's workspace, in the session's worktree folder. It matters most for SSH workspaces (phase 5), where you would otherwise open a separate terminal and ssh in by hand; it works for the local machine too. Built 23 Nov 2026; decisions and checks: docs/decisions/2026-11-23-console.md.

  • In the browser: @xterm/xterm 6.0.0 (xterm.js, the terminal that VS Code uses) with @xterm/addon-fit 0.11.0. We build no terminal ourselves. The shell starts when the tab is first shown and keeps running while other tabs show.
  • On the workspace: the relay starts $SHELL (a login shell, /bin/sh when unset) in a pseudo-terminal with Bun's built-in Bun.spawn({terminal}), so no native add-on such as node-pty is needed. It works inside the compiled Linux binary: the compiled-app smoke test has a step for it (the tenth).
  • In between: keystrokes, output and window resizes travel over the relay connection that already exists (relay/terminal.open, .write, .resize, .close, and the notifications relay/terminal.data and .exit), so a remote console needs no extra port or second SSH login. A terminal belongs to the connection that opened it, at most 8 per connection, and ends when its connection ends, when the session is archived or when the daemon stops.
  • A console belongs to the user, not to the agent. The relay still never advertises the ACP terminal capability to agents, and the Modify agent still runs no shell commands. The shell's environment is the relay's, minus BUN_BE_BUN, BUN_INSTALL_CACHE_DIR and every AGENTCONTROL_* variable, plus the session's PORT and AGENTCONTROL_PORT_BASE.
  • The browser reaches the terminal through a WebSocket endpoint of the app (GET /api/sessions/:id/terminal), guarded by the same Host and Origin checks as the API. The secret travels in the Sec-WebSocket-Protocol header, never in the address, because a browser cannot set headers on a WebSocket and addresses end up in logs and history.
  • Closing the tab ends the shell. A console that survives a disconnect (like tmux) is a later question.
  • Not verified: on macOS (the Mac CI job runs the same smoke step). Output is bounded: while 4 MB or more is unread, big pieces are dropped and an "[output skipped]" line marks the gap, in the relay and in the app, so an endless printer cannot fill memory. A stale token on the terminal socket reloads the page like any other stale token. Open (in TASKS.md): a terminal opened exactly while its connection closes can leak its shell; the skipped-output line is lost if the shell ends mid-drop; a flood in one terminal can drop big output of another on the same relay connection. The internal variables BUN_BE_BUN and BUN_INSTALL_CACHE_DIR no longer reach agent processes (see the adapter launch decision).

How a change is deployed inspect, plan, apply
  1. Inspect. The relay reads what each agent has today on the workspace. On first connect, the UI offers to import it, so existing setups aren't lost.
  2. Plan. The relay translates the canonical items into each agent's native files and returns the file-level diff. The UI shows it before anything is written.
  3. Apply. The relay backs up the touched files, writes the new ones, and reports per agent. Rollback restores the backup.
  4. Watch for drift. The relay rechecks file hashes on connect. If someone edited a file by hand, the item is marked as drifted with options to adopt the change or overwrite it.

Only entries the app created are touched. Managed entries carry a marker and a hash in a manifest (.agentcontrol/managed.json in the config home), so hand-written config around them is left alone. Apply is refused if a file changed after the plan was made. An imported item that matches a file exactly is adopted without rewriting it.

The malleable part · backend and panel built

How the UI rewrites itself

The UI is a small web project inside the app's data folder. A built-in Modify agent edits it on request. The user only sees the result and two buttons: Keep and Undo.

  1. The user asks for a change, for example "add a cost column and sort by it".
  2. The Modify agent, a local ACP session of Claude Code or Codex (a relay directory session), edits a staging copy of the UI.
  3. When the agent's turn ends, the app runs a typecheck and a build. Errors go back to the agent until they pass, or the attempt is shown as failed with the reason.
  4. The finished change is copied to the live folder at once, and Vite hot-reloads it.
  5. Keep commits the change to a hidden git repository, with the request as the message. Undo goes back one commit.

Built as described, with these differences. A change waiting for Keep or Undo survives an app restart. The rules for the agent are text shipped with each app release and sent as the first message of every Modify session; the AGENTS.md in the staging folder is not read for them, because the agent can edit that file and must not be able to loosen its own rules. The fence is enforced by the relay, not by the app: the relay answers every permission request of a directory session and approves only file edits inside ui-staging/. The checks are typecheck and build; the planned lint and browser-load checks are not built.

Never lock the user out. /_safe is served by the app, not by the user's UI. It needs neither the UI folder nor the SDK, and offers Undo last change and Restore for earlier versions, so any broken change can be rolled back in one click. It also has a box to ask the Modify agent for a change, with Keep and Undo. Built and tested with a deliberately broken UI.

Why hot reload is instant

Vite serves each source file as its own ES module and keeps a WebSocket open to the page. When a file changes, it converts only that file and tells the browser to re-import it; React Fast Refresh swaps the component in place and keeps its state. Cost scales with the size of the change, not the app.

Changes in a non-component file bubble up to the nearest importer that can accept them, or trigger a full page reload. That is why the agent works in staging and the live folder gets one clean update.

Updating the default UI merge, agent fixes conflicts, checks, Keep or Undo built
  1. The new app version commits its default UI onto upstream.
  2. In the staging folder, upstream is merged into main. Clean merges need nothing more.
  3. For each conflict, the Modify agent gets the conflicted files and the original requests behind the user's changes, so it rebuilds what the user wanted, not just the old lines.
  4. The checks run: typecheck and build (lint and a browser load test are planned).
  5. The user sees a summary, for example "Update 1.2: 4 of your changes kept automatically, 1 conflict resolved (cost column moved to the new session table)", then Keep or Undo.

Merge, not rebase. A rebase replays each change one by one, so one conflict can come back several times. A merge brings both histories together once, so each conflict is resolved once. The result is the same: the user's changes on top of the latest default UI.

An update never breaks the UI. If the agent can't make the checks pass, the current UI keeps running, the update waits, and /_safe still rolls back.

Keeping conflicts rare.

  • Layout changes go in layout.json; data merges far more cleanly than code.
  • New features go in the user's own files, plugged into named slots the default UI provides (session row, toolbar, side panels), so template updates rarely touch them.
  • @agentcontrol/sdk stays backward compatible: a function is deprecated for one release before removal. If a removal slips through, the typecheck catches it during the update.

Code architecture and quality

Maintainable by default, enforced by the build

The code must stay easy to change after hundreds of agent-written commits. The rules are written down once in AGENTS.md, and every rule a tool can check is checked on every push. A rule only in a document will be broken; a rule in CI breaks the build instead.

Principles

  • Single responsibility first. One module, one reason to change. If describing a file needs "and", split it.
  • KISS. Plain functions and modules. No abstraction until the second real use, no DI framework, no clever types, no utils/ dumping ground.
  • Open/closed where it pays. Agents and harness translators sit behind one small interface each, so adding an agent means adding one adapter.
  • Small interfaces, injected edges. Logic receives its store, transport and clock as parameters. Only the edges (ACP, SSH, SQLite, fs, HTTP) touch the outside world.

Tests

  • End-to-end only. No unit tests. Every test starts the real app and relay and drives them as a user would.
  • GIVEN / WHEN / THEN with a plain-language sentence at every step, saying exactly what is set up, done and checked.
  • Setup helpers and assertion helpers named after the domain fact, so the test reads as a specification.
  • The only fake is the agent: a scripted mock ACP agent, so tests are deterministic and need no API key.
  • At least 95% of lines covered by the end-to-end suite, in total and on changed lines, before any push. Built: about 98.6 to 98.9% today (the last full run), the default UI included.

  • Thin edges, plain core. Adapters translate ACP, SSH, SQLite and HTTP into plain data; the logic in between is ordinary functions over that data.

  • Package rules are enforced: the UI talks only to the SDK, the relay never imports the app, nothing imports a feature's internals, and there are no circular imports.

Development loop how parallel agents change the code without breaking main

From docs/dev-loop-review.md, written after seven agents worked at once, main had never been green, and several finished commits were stuck. The orchestrator is Claude; coding subagents (Sonnet) and research subagents (Opus) do the work, each in an isolated worktree. What exists today: bun run integrate, bun run done, bun run check and check:quick, the dependency and no-git add -A guards, the decision log (15 files), a landing log, the coverage gate, and CI that is green on main, the Mac build job included. What is still planned is listed in the last bullet.

  • One worktree and one branch per agent, started from the latest main and kept outside the tools' view (the agent worktree folder is ignored by git and ESLint). An agent edits only the paths its brief names (docs/brief-template.md is the template).
  • Contracts first. Before a parallel wave, the orchestrator commits the interfaces as code: zod schemas and types in packages/protocol, new SDK signatures, and the end-to-end tests for the feature written as test.todo with full GIVEN / WHEN / THEN bodies. The agents turn the todos into passing tests. If a contract is wrong, the agent stops and reports.
  • An integrate script is the only way onto main. bun run integrate <branch> rebases the branch in a scratch worktree, runs the full check there, and only then moves main (a fast-forward). If main moved in the meantime it stops and is run again. If main ever goes red, the offending commit is reverted first, before anything else.
  • Parallel, timed gates and a quick check. bun run check starts every gate at once, prints seconds per gate and shows all failures. bun run check:quick checks only the changed files and finishes in seconds.
  • A done report. bun run done <paths> runs the full check, fails when files outside the owned paths changed, when a dependency changed, when eslint.config.js changed, or when a new eslint-disable was added, and prints a DONE-REPORT block the orchestrator reads instead of prose.
  • Guardrails. No git add -A or git add .. No repo-wide formatting (bun run format touches only changed files). Dependencies are added only by the orchestrator: a pre-commit guard blocks anyone else from changing bun.lock or a package.json dependency list. Gate samples are written in a scratch copy, so a bad sample is never committed by accident.
  • A decision log. One short file per decision in docs/decisions/ (context, decision, rejected options, consequences), written on the agent's branch so it merges with the code. The first file, 0001-dev-loop, records these decisions.
  • Lessons from the first two days (22 and 23 Nov 2026), stated plainly:
    • Tests run from a git hook inherited git's environment and changed the repository's own settings. Inside a hook git sets GIT_DIR; tests that created their own repositories ran git init, git config and commits against this repository, which ended up marked bare with a test identity. Fixed: the relay's git calls and the test runner drop git's variables, and the pre-push hook clears them.
    • Too many agents on a 4-core machine made tests time out. Several agents each running the full suite at once starved each other, and timing-sensitive tests failed for no code reason. Work was paused until the machine had room. The tests have no timing budget yet; the rule for now is fewer parallel agents, and the suite stays free of sleeps.
    • CI was red on GitHub while local checks were green, because nobody looked. main had never been green on GitHub for the first day. When it was looked at, the causes were small (an unpinned Playwright, a shallow checkout, scripts that were not executable). It first went green on 23 Nov. The integrate script only proves a branch on the machine it runs on, so someone has to read the CI result after every landing. The Mac job in build was red for a few hours on 23 Nov and went green with the version fix described next.
    • A change that passed every gate broke the compiled app. The shared VERSION read the root package.json (absent in a release folder) and the smoke test expected the old health answer. The compiled-app smoke was not in the pre-landing path, so only the Mac runner noticed. The orchestrator now runs bun run build:linux and the app smoke before each landing; putting the smoke into bun run integrate is being done now.
    • Three features built in parallel conflicted in the same three UI files. The workspace picker, the Config screen and the Console all edited App.tsx, data/controller.ts and panes/dialogs.tsx, and needed two extra merge rounds. Next time each feature gets a registration point first: a list of screens, dialogs and tabs to which each feature adds one line, instead of editing the shared switchboards.
    • CI was red for five landings because only half of it was read. After each landing on 23 Nov the orchestrator read the build result (the Mac job) and not ci. ci had been red since the Console landed: one terminal test compared raw terminal output, and the GitHub runner's shell wraps every command's output in invisible control sequences, so the expected line never matched. The first fix was a guess (wait for a prompt) and did not work; the second came from a raw capture on the runner, taken on a queue/** branch. Rules that follow: read every workflow after every landing; when a failure does not reproduce locally, capture evidence on a queue branch before changing anything; a failure message must show what a person would see, not the last bytes. Red runs now end with the failing test names.
  • Planned: golden files for the durable state. Real event logs (including one cut off mid-line), a snapshot of the relay protocol with a protocol version number that must change when a field is removed, an old state.db per migration that the app must still open, and an old hidden UI repository that must upgrade cleanly. Also planned: a coverage map of every relay method, event kind and API route, a timing budget per test, a nightly flake run, and a status page generated from the repository.

Risks and open questions

Risks

  • ACP adapters lag behind native CLIs; some features may never appear in events.
  • Agent-written UI code breaks in ways a typecheck misses.
  • Thinking varies by vendor: summaries rather than raw reasoning.
  • Shared UIs are code with full access to your agents.
  • Config formats change between harness versions and can silently break translations.
  • Aggressive limits slow early work and invite rule disabling; the reason-required rule and review must hold the line.
  • An e2e-only suite is slower; it must stay parallel and free of sleeps to keep feedback fast.
  • Codex is unverified end to end. The OpenAI key we had has no quota, so only start-up and sign-in were seen. Streaming, diffs, permissions and the Manual-mode behaviour are not confirmed, and there are no recordings of it.
  • The Mac app has never been run on a Mac by a person. The Mac runner builds both apps, runs the compiled app from the bundle and from the dmg, and the build is green, but nobody has opened the dmg on a real Mac (Gatekeeper), launched the menu bar app, or run it on Intel. Expect fixes on the first real run.
  • The release is about 700 MB per platform (the default UI ships with its own node_modules, and the app carries two Linux relays). Nothing is trimmed; whether that is acceptable to download is open.
  • The Modify agent's launch limits exist only for Claude Code. For Codex the relay's permission answers are the only fence, and Codex as the Modify agent has not been tried.
  • A session does not survive a relay restart. Claude can load the old session, so resuming is possible; relay/sessions.resume is being built now. On main today such a session reads as idle and the next prompt fails with "agent is not running".
  • Remote (SSH) workspaces are only proven against a local sshd. The backend and the UI are on main. A real remote Linux host and arm64 are unverified. Sessions resume after a relay restart (tested with the mock agent and a local sshd).
  • The test suite is sensitive to load. On a busy 4-core machine, timing-dependent tests failed without any code change. There is no timing budget or flake run yet; fixes for the flakiest tests, and the compiled-app smoke inside bun run integrate, are in progress.
  • The mock agent can still drift from the real adapters. Recordings of real Claude Code now guard the update shapes, but Codex has none, and no check yet proves that every update kind the mock emits appears in a recording.
  • Local server security has a known edge. Other programs running as the same user can read the token file, and another local process that can reach the port can read the token from the served page. That is the operating system's boundary and was accepted; a one-time launch URL would close the second case.
  • The unsigned release trains users to bypass Gatekeeper. Accepted for the first release; the README explains the steps.
